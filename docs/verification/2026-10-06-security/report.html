Showtime security investigation

6 October 2026 · Deployed production and UAT · Read-only review and controlled local tests

Four independent reviewers examined account authentication, browser behavior, notifications, and content/infrastructure. Three Medium findings were reproduced locally using deployed code and independently cross-reviewed. These are confirmed code behaviors, not attacks carried out against live users. No High or Critical runtime issue was demonstrated within the reviewed scope.

1. Password-reset recovery can miss an in-flight login

Severity: Medium. Impact: a session issued using the compromised old password can remain valid after reset, undermining recovery. The configured session lifetime is 30 days, subject to subsequent revocation or reset.

Exact deployed references: deployed/showtime-api-index.js:1266 (unconditional session insert), :1304 (atomic reset/password change and session deletion), :1422 (login verification then issuance), :1442 (session resolution). Original source module comments identify src/auth/db.ts and src/api/auth.ts; original TypeScript line numbers cannot be recovered reliably without source maps/source.

Prerequisites: the attacker already knows the old valid password. Login must verify the old hash before reset commits and insert its session after reset commits. A normal sequential login with the old password after reset is not shown to work. Live race success probability was not measured; authentication rate limits constrain attempts.

Evidence: accounts-review/probe.mjs executes actual deployed password verification, login and session resolution with a mocked database. The interleaved case returned 200 and the session resolved after the modeled reset. Independent notification reviewer reproduced it. Parent independently executed actual reset SQL in SQLite: reset invalidated the token and existing sessions, yet the production unconditional insert still succeeded afterward. The UAT conditional insert with the old hash returned no row. Results are in evidence/sqlite-auth-validation.json.

Fix: atomically create a session only when the current password hash still equals the verified hash; fail login if no row is inserted. UAT bundle already contains this pattern at deployed/showtime-uat-api-index.js:1526. Alternatively bind sessions to an authentication generation checked on every resolution. A separate pre-insert recheck leaves another race. Production promotion requires the original matching source, tests and normal release/migration review; none was undertaken.

2. Shared-browser library transfer lacks consent

Severity: Medium privacy design risk. Impact: retained data from account A is uploaded into account B’s cloud library without an explicit transfer decision.

Exact served references: browser-review/prod.js:949 (logout removes the session but retains library), :955 (global collection keys), :965 (account-scoped sync metadata reads global library), :1029 (sign-out UI). The file is the retrieved production entry asset with stable captured line numbers.

Prerequisites: A and B share the same browser profile/origin. A leaves library data and signs out. B signs into a different verified account whose relevant cloud collection is empty. No remote credential theft or server-side tenant bypass is established.

Evidence: browser-review/reproduce-library.cjs runs exact deployed sync and validator modules against synthetic storage and cloud transport. Account A’s synthetic watchlist is pushed with account B’s synthetic session. Parent and content reviewer reran the test. The populated-cloud merge branch was not separately reproduced.

Important qualification: historical docs/SYNC-DESIGN.md:25 explicitly specifies this retained-library merge and advises clearing browser data before sharing. This is intentional product behavior with missing runtime consent, not an unexpected regression. Local retained data was already available to another user of the browser profile; the additional impact is cloud persistence under another account.

Fix: scope active libraries by account, or retain ownership metadata and require explicit consent to import another account’s retained library. Preserve deliberate guest import and optional guest mode while keeping account transitions and in-flight sync writes consistent.

3. Anonymous enrollment can exhaust notification capacity

Severity: Medium availability issue. Impact: notification enrollment becomes unavailable to legitimate users. This does not demonstrate website downtime or private-data access.

Exact deployed references: deployed/showtime-notifications-worker.js:445 (request handler), :467 (registration limit and capacity check); UAT deployed/showtime-uat-notifications-worker.js:483 (handler). Public web forwarding is visible at deployed/showtime-web-worker.js:5 and equivalent UAT gateway. Notification subreport uses original multipart line numbers, which include four additional MIME header lines.

Verified capacity: production allows 20 devices, 60 distinct shows and 7 schedule reads per run. UAT defaults to 4 devices, 24 distinct shows and 4 schedule reads. New registration allows ten per IP/hour. The ID and token for a new device are caller-selected, rather than an existing account, invite or admission grant.

Prerequisites: public enrollment is reachable and slots remain. A caller can reserve available slots within permitted hourly buckets. Even UAT cryptographic validation establishes only locally valid key material, not a genuine provider-issued subscription; fabricated endpoints on an allowed push hostname pass registration. This was tested locally only. Scheduled provider failures may reclaim some records later; production invalid-curve records fail before provider contact and can continue occupying capacity. Retention is otherwise up to 180 days and owner renewal can extend it.

Evidence: notifications-review/proof.mjs invokes exact deployed handlers with mocked D1. Production returned 20 successful admissions then 503; UAT returned four then 503. Mock hourly buckets were explicitly reset to model separate permitted buckets, not a rate-limit bypass. Zero push/network requests occurred. Browser reviewer independently validated gateway exposure, conditions and proof. Real device rows were never inserted.

Fix: require an account/invite or server-issued admission capability appropriate to this intentionally small pool; enforce per-principal quotas and short provisional leases, with reclamation and monitoring. Retain atomic capacity constraints. IP limits alone, particularly limits larger than the whole UAT pool, cannot solve admission fairness.

Additional observations and uncertainty

  • Low: account existence disclosure. Actual production signup handler returns 409 with “An account with this email already exists.” for an existing email. accounts-review/probe-results.jsonl records a local existing-user branch without email or mutation. Rate limits constrain enumeration. If membership is sensitive, use a generic registration response; product policy may accept this disclosure.
  • Informational: malformed production push keys. Production accepts syntactically sized invalid curve keys; UAT rejects them. Failed pre-send encryption can strand claimed events in production. Principal impact is on the registering device, and it facilitates capacity squatting; it is not counted as a separate cross-user vulnerability. Port UAT validation and pre-send failure recovery with delivery lifecycle migration compatibility checks during an authorized release.
  • Hardening: HSTS absent from sampled HTML responses. Bearer sessions/device secrets are accessible to same-origin JavaScript in local storage; no exploitable XSS was established.
  • Unverified UAT availability concern: gateway content requests omit incoming client-IP headers, while API limiter falls back to “anonymous.” Cloudflare service binding metadata may synthesize client identity, so shared limiter collapse is not proven live. Verify in an isolated runtime fixture before changing trusted forwarding behavior. No saturation test was performed.

Controlled testing and verified controls

All five local JavaScript evidence scripts were rerun by the coordinating reviewer and passed. A separate SQLite test confirmed actual production reset SQL, used-token rejection and UAT conditional-session rejection. These checks establish described code behavior, not Cloudflare runtime timing, D1 schema health or a complete browser session test.

  • Content validation: nine malformed local cases and three lightweight live malformed API requests returned expected rejection; live cases terminate before upstream work and are uncached.
  • Upstream safety: five local invalid endpoint cases blocked before fetch; credential-bearing redirect rejected; fixed HTTPS TMDB origin and constrained paths; bounded response size and timeouts.
  • Fanout: 100-season fixture dispatched 12 season reads at maximum concurrency three. UAT work-budget test allowed only two actual mocked dispatches before denial closed further work.
  • Sync: authenticated owner was bound even when a payload supplied another user ID; no server IDOR reproduced in that tested path.
  • Reset: actual SQLite reset token cannot be reused; existing sessions are deleted atomically. The separate in-flight issuance race remains as above.
  • Browser: restrictive CSP, frame denial, nosniff, fixed-host legacy redirect, safe service-worker notification destinations, and backup credential exclusion observed. No application XSS or open redirect demonstrated.
  • Push: exact HTTPS provider-host allowlist and redirect refusal reviewed; no arbitrary-host SSRF or device ownership bypass demonstrated.

Full reproduction and peer assessments are under accounts-review/, browser-review/, notifications-review/ and content-review/. Served frontend hashes/URLs are documented in the browser evidence.

Limits and next actions

No deployments, migrations, production writes, destructive requests, load attacks, real email/push deliveries or customer database reads were performed. Evidence uses synthetic credentials and records. Public HTML/assets and bounded GET/HEAD/OPTIONS checks were retrieved; local proofs replace network/database services with controlled fixtures.

The original edited source, current lockfiles, exact migration state, database recovery readiness, current CI/build provenance and live account/device race timing remain unavailable or untested. No claim of “secure” follows from these results. The missing current source prevents a trustworthy implementation PR or release; reconstructing compiled bundles does not recover tests/migrations fully.

Priority: recover current source; apply/review the atomic login issuance fix; add deliberate account-library transfer choices; protect notification admission. Then verify migrations and matching service compatibility as a separate authorized release. This report was not published to UAT because publication would change its deployment.
